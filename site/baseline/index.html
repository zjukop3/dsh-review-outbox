生态基线：下载数在什么区间才有信息量

首页发布与收录手册装不上怎么办GitHub 源码

2026-11-10 实测。目的只有一个：在自己身上或者其他插件身上看到一个下载数时，能判断它到底说明了什么。

结论先写：这个生态里，「周下载 200–400」不代表有人在用。 一个没人安装的插件也会稳定出现每天二三十次下载。目录里 58.6% 的条目就停在这一层。

三个带

  • 底部带 ≤40/天：与是否有人安装无关。抽样里 dsh-feedback-bridge 是 7 天 23/29/30/20/30/21/29 这种平坦曲线，没有任何推广痕迹；dsh-notch-focus 是 21/204/30/26/32/42/26，中间那天是发布。两者周总数都不低，用法完全不同。
  • 可见带 40–150/天：说明有稳定的、非发布驱动的取用。
  • 真实日用 >150/天：只有 6.1% 的条目到这里，绝对值上约 300 个包。

底部带的成因没有定论：镜像同步、爬虫、还是少数装着就忘了的静默安装，这三者从下载数据里分不开。能确定的只是它与采用无关，所以任何拿它当成绩的说法都不成立。

我自己在这一层的位置

dsh-review-outbox 上周 497 次，全在 2026-11-08 发布当天，其余每天 0。按全量排序是 1,971 / 4,978，即前 39.6%。

这个前 39.6% 不该被当成成绩：497 与中位数 381 的差落在底部带的波动里，形状上它和一个发布了没人用的包无法区分。同一时期，真实日用的邻接插件是 dsh-better-sidebar 10–15k/天、dsh-pet 15–25k/天、目录包本身 12–17k/天。

因此本项目的采用度量从这一轮起改用两个能验的东西：人工决策漏斗（scripts/report-usage.mjs）和验收单摘要可核对（scripts/verify-receipt.mjs）。下载数只作为「镜子有没有坏」的检查，不作结论。

复现

# 全量周分布（约 10 分钟，含 scoped 包逐个查询）
node scripts/ecosystem-snapshot.mjs --package dsh-review-outbox

# 200 个包的 30 天形状（抽样确定，seed 固定；结果缓存在 docs/metrics/ecosystem-downloads.json）
node scripts/ecosystem-snapshot.mjs --shapes 200 --seed 20261110

原始数字：docs/metrics/2026-11-10-ecosystem-baseline.json。

已知不确定项

  • npm 下载接口有约两天延迟，最近两天的日值一律是 0，不能读成「没人下载」。
  • 抽样是名字空间的均匀随机，没有按类别或发布时间分层；新发布的包天然更容易落在「爆发型」。
  • 周下载与日序列取自不同窗口（相差一天），两者不能逐包相减。
