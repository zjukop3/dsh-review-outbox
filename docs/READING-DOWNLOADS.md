# 怎么看自己的下载数：三种形状，一种信号

写这份东西的原因是：这个生态系统里每一个新作者都会看到自己的下载数上涨，然后高估它。包括我。这份文档给的是**一个能自己跑的判别方法**，不是安慰，也不是劝退。

所有数字都可以用文末的命令复现。测于 2026-11-10 至 11-18。

---

## 一、先知道底噪有多大

对目录里随机抽 200 个包，取 30 天的日下载序列，按形状分类：

| 形状 | 2026-11-10（随机 200 包） | 2026-11-15 复测 | 2026-11-16 复测 |
|---|---:|---:|---:|
| 停在底噪带（≤40/天） | 58.6% | 60.1% | 63.8% |
| 静默（≤10/天） | — | 24.7% | 26.1% |
| 发布日爆发形 | 19.7% | 28.3% | 20.6% |

三个时间点的底噪带占比在 58.6%–63.8% 之间。**也就是说：目录里大约六成的包，日下载长期停在 20–40 次，和有没有人用无关。**

那一层是镜像同步、索引器、CI 缓存。它们的共同特征是**跨包均匀**——下一节就是怎么用这一点。

## 二、三种形状

拿到一个包的日下载序列，先看形状，再看总量。

**形状 A：发布日爆发 → 衰减到尾**

```
2026-11-10: 302   2026-11-11: 15   2026-11-12: 10   2026-11-13: 8
```

一天吃掉大半周量，然后掉到个位数。这是**发布日索引器**：镜像拉了一次、索引器扫了一遍、某个聚合服务缓存了 tarball。它不是使用。

判据：`单日最大值 / 全周总量 ≥ 50%`，且尾部落在底噪带内。

**形状 B：平坦底噪**

七天全部在 20–40 之间，没有尖峰。这是**被持续扫描**，不是被持续使用。判据：`尾部三天均值 ≤ 40/天`。

**形状 C：持续高于底噪带**

尾部三天都在 100 以上，且没有单日占掉一半。这是**第一种可能是人的形状**——但先别下结论，看下一节。

## 三、第三种形状里最容易犯的错：不看分散度

2026-11-18 实测我自己的九个包（发布 8–10 天），尾部三天均值：

```
117  119  121  122  164  171  178  180 /天    变异系数 CV = 0.186
```

九个**不同的工具**，速率落在彼此的 19% 以内。

这个数字本身就是答案：**人们真正选择使用的九个工具，不会彼此相差 19% 以内。** 有用程度不同的工具，用量应该分开——一个查合同的工具和一个查 LICENSE 的工具，受众规模差几个量级。落得这么均匀，只有一个解释：**一个自动客户端在同时拉取它们**，每包每天同样几次。

**判据：跨工具的尾部速率变异系数 < 0.25 → 按自动化处理，不管水位多高。**

一条推论值得记住：**均匀性比水位更有说服力。** 100/天 且九个包都在 95–105 之间，几乎一定是自动化；40/天 但两个包是 120 而七个是 8，反而可能是真实使用。

## 四、那什么才算信号

这个项目现在只认两个能被验的东西：

1. **人工决策数**：有人读完一份成果、写下证据、点了通过。这个数字不能自动化，也不能靠下载刷出来。
2. **验收单摘要可核对**：导出的验收单带被审文件的 SHA-256，文件事后被改动，同一份验收单会明确提示重新审阅。

两者都不是下载数。下载数是**输入**（有多少机器看过），不是**结果**（有多少人因此做了什么）。

## 五、自己跑一遍

```bash
# 目录分布的底噪带（约 10 分钟，全目录）
node scripts/ecosystem-snapshot.mjs --package 你的包名

# 抽样看形状（30 天序列，200 个包）
node scripts/ecosystem-snapshot.mjs --shapes 200 --seed 20261110

# 按周下载排名分层（回答「榜单有没有被发版日抬高」）
node scripts/ecosystem-snapshot.mjs --shapes-rank 200

# 自己的全部包：周量、发布天数、日形状、尾部三天、跨包分散度
node scripts/portfolio-signal.mjs
```

最后一条是本文第三节那个判断的实现。它会在输出里直接说结论，包括对自己不利的那种。

## 六、我因为这个方法改过什么

写下来是为了说明这套东西不是事后合理化：

- **撤回过一份提案。** 我向官方市场提过「下载列加发布日标记」的建议。维护者说：如果你的数据能说明发版日形状在**排序**上造成排错，我们可以重新看。我跑了排名分层测量：TOP-200 的爆发形占比 10.8%，全目录 28.0%——**方向相反，榜单没有被发版日抬高**。数据不支持自己的提案，撤回了。
- **推翻过自己的一个读数。** 一度以为 82% 集中两天是榜单常态，分层测量后发现自己的包才是那 10.8% 的例外。
- **改正过测量工具的一个 bug。** 采样脚本有一个把数组索引当成包名的回归，产出过 63 和 66 个「名为 0、1、2 的包」的废数据。发现后修掉、重跑，并把废跑写进记录。

方法是自己的，就得对自己的结论一样苛刻。否则它不是方法，是修辞。
