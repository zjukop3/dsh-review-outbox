# Review Outbox：长期生态路线

## 产品判断

DSH 生态不缺少通用工作流、通知中心或文件仓库。值得验证的是更窄的一层：**Agent 已经产出结果以后，人怎样高效地完成审阅、退回和处置。**

Review Outbox 不追求成为新的 Agent Runner，也不处理 DeepCanary 已覆盖的普通提醒。它面向交付物、变更和垂直作品，目标是成为多个插件共享的成果审阅层。

### 2026-11-10：定位修正

目录里已经有 4,985 个条目、321 个 workflow 插件，其中 68 个与审阅/验收沾边。**「带版本绑定的交付回执」已经有人做了**（`@oxmumu3/dsh-delivery-receipts`：“Session-scoped artifact receipts with file evidence and version-bound user decisions”），所以把回执当卖点是打不响的。

同带里的邻接插件月下载在 700–3000（`dsh-session-insights` 3033、`dsh-delivery-kit` 2996、`dsh-outcomes` 1487、`dsh-oracle-gate` 866、`dsh-review-squad` 769），说明这一层有真实需求，天花板不小；我们自己是 497，且全部集中在发布当天，无法归因给人。

**结论：卖点改成「研究报告的证据门」**——结论、引用、数据口径、方法限制四项必填检查，勾选之外必须写证据；回执只是"门被通过"的产物，不是产品本身。标题、描述和首屏都按这个顺序讲。

## 自然增长模型

单纯的通用审阅工具缺少明确的自然搜索入口，不能依赖维护者持续在社交媒体推广。产品必须把获客做进使用过程和交付物，形成“搜索或成果发现 → 安装 → 完成验收 → 成果携带验收单 → 新用户发现”的循环。

### 场景搜索环

核心插件保持单一，不批量制造低质量插件。围绕已有任务意图提供可搜索、可独立使用的验收包，首批候选是研究报告事实与引用验收、PPT/文档交付验收、代码变更与发布验收。每个验收包包含检查清单、所需证据、退回意见模板和通过条件；场景包只提供规则与模板，不冒充自动事实核查。

先实现文本成果即可完整使用的研究报告验收包，再用目录、npm 和 GitHub 的搜索数据决定后续场景，不凭想象同时开发多个包。

### 成果携带环

用户可以选择随成果导出一份独立 HTML 验收单，包含成果名称、revision、审阅状态、检查项、意见、文件摘要和插件入口。验收单与原始成果分离，不修改正文、不加水印、不自动发布。用户分享成果时自然携带验收证据，接收者无需安装即可查看，需要处理同类成果时再进入安装流程。

### 零配置与依赖分发环

凡使用官方 `present` 的插件都自动进入 Review Outbox，不要求上游作者逐个适配；`dsh-research-report` 已进一步通过标准 Session 工具事件和密封结果 metadata 自动接入。后续提供版本化验收规则和验收单数据结构，让垂直插件可以把本插件作为可选审阅层或开发依赖，通过依赖关系获得分发，而不是依靠人工互推。

### 获客纪律

Awesome、插件市场、npm、GitHub 和可搜索的场景文档是主要发布面；社交媒体只作补充，不设发帖数量目标，不把人工互推当成增长前提。目录收录只是搜索入口，不是增长完成的证据。

## 北极星与护栏

**北极星指标：每周被真正审阅并处置的成果数。**

辅助指标：

- 每周完成至少一次审阅的用户数
- 第二周仍继续审阅的用户比例
- 被退回后再次交付并最终通过的 revision 数
- 来自非本插件原生适配的成果比例
- 场景搜索到首次验收的激活率
- 验收单导出数，以及能够可靠归因的验收单入口激活数
- 零配置官方事件接入占比、接入的垂直插件和二级扩展数量
- 被上游合并的贡献、真实 issue 解决数和外部维护者数量

不设置单纯追求 npm 下载、Star 或榜单曝光的目标。它们可以记录，但不用于决定产品方向。

## 阶段路线

### M0：合成环境与真实挂载验证（已完成）

交付：

- Host/Client 可安装骨架和持久状态
- 官方事件转换与模拟事件集成测试
- 文本/图片预览、审阅动作与 revision
- 隔离 DSH 的真实 API 和浏览器操作验证
- 重启后的状态恢复验证

通过标准：45 项测试、真实 API、真实浏览器和重启检查全部保留证据；官方 `present` 的生产压缩落盘、历史冷读回填和跨 `callId` 的真实 revision 也已覆盖。

### M1：自己的真实工作流（工作项完成，日常使用持续中）

目标：在日常使用中回答“它是否减少了漏审和重复打开会话”。

工作：

- 在真实 DSH 会话中交付至少 20 个成果，记录首次价值时间和退回原因。（已完成：[Dogfood 报告](DOGFOOD.md)记录 5 组任务 20 个成果、5 项退回修复、完整 revision 链与重启持久化。）
- 完成一次官方 `present` 录制/回放测试，区分模拟事件与真实工具链路。（已完成：`test/official-present.test.js`。）
- 补历史 Session 的 `deliverables/presented` 回填，明确扫描上限与隐私边界。（已完成。）
- 复用宿主文档预览或 better-sidebar Viewer，避免自研 Office/PDF 渲染器（已完成 DOCX/PDF 真实链路，其他格式继续验证）。
- 用真实成果定义研究报告验收包和独立 HTML 验收单的最小格式，验证它们确实被使用，而不是只增加展示功能。（已完成：两份研究文档执行完整验收包。）
- 建立 DSH 版本与安装矩阵，覆盖 npm、GitHub 和 Release 预编译包（Node/DSH/tarball 矩阵已建立，GitHub 仓库、Pages tarball 与 npm `0.1.2` 已公开，GitHub Release 尚未发布）。

退出条件：至少 5 次独立真实任务愿意继续使用；若没有，回到问题定义，不扩功能。Dogfood 是脚本化真实审阅，"愿意继续使用"的最终判定依赖维护者日常真实工作流的持续采用，该项保持进行中，不提前宣布完成。

### M2：公开 Alpha 与自然获客验证（基础设施就绪，等待外部信号）

目标：验证成果审阅是不是跨用户、跨插件的共同问题，以及产品自身能否带来非人工引荐的激活。

工作：

- 通过一个研究报告验收包验证场景搜索，不同时铺开多个低证据场景。（已完成：[研究报告验收清单站点](https://zjukop3.github.io/dsh-review-outbox/research-report/)与应用内索引上线。）
- 提供独立 HTML 验收单，验证成果接收者无需安装即可查看、需要时能进入安装流程。（已完成：`0.1.2` 验收单入口直接回到安装指南，见[首次价值证据](e2e/application-first-value.json)。）
- 优先复用标准 Session 工具事件，已完成 better-sidebar 的可选界面集成和 `dsh-research-report` 的密封成果自动接入；真实外部审阅流量仍待验证。
- 提供中英文 README、90 秒演示、安装与恢复指南，以及可被搜索引用的真实验收案例。（README 双语、安装恢复指南、可搜索案例与真实截图已就绪；[20 秒审阅流程演示 GIF](https://github.com/zjukop3/dsh-review-outbox#readme) 已录制并嵌入双语 README——覆盖回填、证据填写、通过与验收单导出，替代原计划的 90 秒视频。）
- 通过目录、应用内 `format: 1` 索引、场景模板页和验收单入口开放 Alpha，不把维护者的人肉社交媒体推广作为获客前提；公开索引的发现、安装与启用链路已在隔离 Profile 验证，`0.1.2` 已通过公开 Discover 界面完成全流程验证。
- 收集匿名化操作记录，不采集正文、路径、密钥或会话内容；远程遥测只在单独明确 opt-in 后考虑。（未实现，维持默认无遥测。）
- IndexNow 部署通知已上线（HTTP 202 接收证据在案）；搜索引擎收录仍未建立。
- 官方插件市场（dsh-market，11k+ 星标）已收录 0.1.3（npm 源），市场内搜索可命中、卡片正确渲染；目录详情页探针已刷新为当前 README。首次出现 github.com referrer（2 次浏览，不构成激活）。见[市场收录快照](metrics/2026-11-09-market-listing.json)。

退出条件：5 位外部用户完成真实审阅，2 位第二周主动回来，至少 1 位新用户通过场景搜索或验收单入口完成首次验收。截至 [0.1.2 发布快照](metrics/2026-11-08-0.1.2-release.json)，四项激活指标均为 `null`，退出条件未达成。

### M3：成为可组合的平台层（集成指南已发布，实际采用待外部）

工作：

- 为其他插件提供稳定的成果注册与审阅适配器，版本化数据结构。（集成契约已文档化：[插件作者集成指南](INTEGRATION.md)覆盖三条接入路径与边界；版本化场景包开放仍在路线中。）
- 优先为 better-sidebar、歸藏设计、Agentero 等成熟项目做联合工作流。（better-sidebar 联合验证已完成；其余待外部协作。）
- 向官方或成熟插件提交 issue、复现和 PR，先解决共同问题，再扩大自有仓库功能。
- 建立外部贡献指南、适配器示例、兼容策略和发布记录。（集成指南含自查步骤与 Issues 反馈入口；贡献指南待外部贡献出现后补充。）

退出条件：至少 2 个外部插件产生真实审阅流量，至少 1 个外部维护者参与代码或适配器维护。尚未达成。

### M4：可信分发与长期维护

工作：

- 向 Awesome/市场提交时围绕具体任务意图组织标题、关键词和场景页，并提供精确版本、权限说明、安装验证、截图和升级策略。
- 保持 Release 产物与源代码、测试结果、SHA-256 一致。
- 维护兼容版本矩阵、回滚方案与问题响应 SLA。
- 建立社区目录中的真实用户反馈入口，定期公开维护状态。

目标不是“被收录”本身，而是让用户在版本快速变化时仍能可靠安装、升级和恢复。

## 时间分配

- **35% 真实使用与可靠性**：真实任务、兼容、恢复、性能与数据边界。
- **25% 核心产品闭环**：预览、比较、退回、revision 和处置。
- **25% 产品内自然增长**：场景验收包、独立验收单、搜索入口和可靠归因。
- **15% 生态协作与发布面**：零配置接入、上游贡献、目录收录和外部维护者。

如果真实使用证据不足，时间优先转向前两项和成熟项目贡献，不用更多平台功能掩盖问题。

## 决策纪律

1. 不重复做 RoutineKit、DeepCanary 或通用文件库。
2. 不在没有真实成果流时建设大型插件市场或复杂流程引擎。
3. 不用自动发布、自动回写会话等高风险动作换取演示效果。
4. 不把模型自报完成当成成果通过；用户审阅和证据是独立状态。
5. 不为了兼容旧版本悄悄维护多份 Runtime；每个支持范围都有真实验证证据。
6. 不用安装量替代真实审阅行为，不用母项目 Star 替代插件采用。
7. 不把社交媒体发帖、人工互推或批量目录投稿当成自然增长；优先让搜索、官方事件和验收成果自身带来新用户。
8. 验收单必须与原始成果分离且默认不公开，不用修改正文、强制水印或自动上传换取传播。
