# 给目录/市场的信号提案：发布日形状的周数字应带「发布日」标记

**状态**：草案，计划随 2026-12-01 月报正式开 issue。issue 正文紧凑版已预写：[SIGNAL-PROPOSAL-ISSUE.md](SIGNAL-PROPOSAL-ISSUE.md)（当天刷新趋势表与数字后粘贴）。fkysly 在 #13819 的结论里明确邀请「具体的替代信号提案（带可复现的测量）」——本文件就是按这个邀请准备的。开 issue 前先刷新数字——操作顺序见 [MONTHLY-RUNBOOK.md](MONTHLY-RUNBOOK.md)（先 weekly:meta 与账本编辑，再 report:monthly，页面才会读到新元数据）。

## 提案内容（一句话）

列表/市场页的「下载」列，当某个包**单日下载占其周总量 ≥ 50%** 时，显示为「发布日」样式（徽标或斜体）而非裸数字。**不改排序**，只给读者一个不误读的口径。

## 为什么是这一个信号

1. **它可判定**：只需要最近 7 天的日值序列，npm 下载 API 直接给。不需要新的数据源、不需要维护方做任何主观判断。
2. **它抓住的正是误读的高发形状**：发版日固定开销。实测（2026-11-15 运行，窗口 30 天）：
   - 全目录抽样（198 包，seed 20261110）：**19.7%–28.3% 呈单日 ≥5× 中位数的爆发形**（三个测量点：11-10 窗 19.7%、11-15 两次 28.3%/28.1%——占比随目录新增而上升，结构不变）；
   - 自己的包是现成的展品：`dsh-review-outbox` 周下载 1,997、排序 **#335/5,423（前 6.2%）**（11-15 两次运行间目录从 5,290 涨到 5,423，排名随之浮动——目录在加速膨胀），但**前两天的下载占 82%**（11-09 单日 1,131 = 安静日的 8–31 倍），安静日 36–81 落在底噪带（≤40/天，占全目录 58.6%）。按这个数字排序的人会得出「前 6% 的插件」的结论——而它的安静日形状与没人用无法区分。
3. **有独立同行背书**：zuwenyin 在讨论 #11870 独立确认了同一底噪带，并量化其包的发版日开销为安静日的 **8.3 倍**——不同量级、同一种形状。这不是本项目的孤例。
4. **成本极低**：展示层加一个条件样式；探测管线已每天拉 npm 数据，加一步日值序列即可。

## 实现层建议（供维护者参考，不预设）

市场 UI 的下载列数据来自维护方自己的管线。两个可选接入点：

- **索引携带**：format 1 索引的 version 条目本就含 `publishTimestamp`；UI 侧只需「当前时间 − 最新版本发布时间 < 7 天」且「单日 ≥50%」两个条件都满足时打标。
- **UI 自查**：不走索引，UI 直接拉 npm downloads API 的日值序列（`/downloads/range/`），同样两个条件。

两者都不需要新的数据源或人工标记。

## 已被明确拒绝的替代项（不再提）

- 换排序口径 / 换信号源 —— fkysly 在 #13819 已给维护者结论：不值得。本提案**不动排序**。

```bash
node scripts/ecosystem-snapshot.mjs --package dsh-review-outbox    # 展品的全量数据
```

原始数字：`docs/metrics/2026-11-15-ecosystem-weekly.json`（含上游账本与 zuwenyin 背书记录）；方法论：`docs/ECOSYSTEM-BASELINE.md`；月报页：`/ecosystem/`（含「本周坐标」区块，每期刷新）。

## 已知不确定项

- npm 日值有上报滞后（最近两天常为 0；zuwenyin 以 react（四千万日下载量级）对照验证过同样的滞后）——判定窗口应排除最近两天，用「前 5 天中某一日 ≥50%」。
- 阈值 50% 是拍的，可按维护者口味调；给出的是机制不是常数。
- 排名数字随目录膨胀浮动（11-15 当天 #318→#335），提交时以当日运行为准。
