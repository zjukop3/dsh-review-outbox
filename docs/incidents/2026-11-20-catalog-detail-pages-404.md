> 错在验证方法，不在条目，也不在站点。保留全文是因为错的推理链比正确结论更有用。

没有造成对外损害的原因只有一条：我在动手改上游之前先做了对照实验。

## 根因

真实的 slug 规则是 `owner/repo--路径用短横连`，站点自己有 `slugOf()`：

```
https://github.com/zjukop3/dsh-vertical-kit/tree/main/packages/dsh-handover-check
  ->  zjukop3/dsh-vertical-kit--packages-dsh-handover-check
```

我拿**自己猜的** `/p/{owner}/{包名}/` 当判据，从没去读站点怎么造 slug。同一个错误在这一系列
工作里是第四次：`\b发票号码`（量正则拼写）、`subject-empty` 用 `.+`（量正则拼写）、
`git push | grep`（量退出码）、这次（量我猜的 URL）。前三次的教训我写进了台账、立了
「规则必须双向观察」的规矩，但那条规矩只管「规则对不对」，没管「喂给规则的输入对不对」。

第二个失误更值得记：904 条同样写法的条目在我的错 URL 下**一致地**失败，我却读成
「站点级缺陷，我无能为力」，而不是「我的测法一致地错」。

## 处置

- 撤回错误结论：incident 改写为自纠复盘，保留错误推理链。
- 脚本改真规则：`scripts/check-detail-pages.mjs` 复刻 `slugOf()` 并导出被测函数，
  在 URL 边界补 `encodeURI`（对齐上游 #13569，规范地址是 `%2520`）。
- 加闸：`test/detail-pages.test.js` 8 条，含上游 #13437 的 `%20` 复现用例、`git+` 前缀、
  非 GitHub URL 返回 null；`docs/metrics/2026-11-20-detail-pages.json` 存方法 + 28/28 实测。
- 实测口径变更：详情页可达从「我猜的 URL 拼法」改为「站点 slug 规则 + 边界编码」，28/28。

## 教训

> 拿不到预期结果时，先怀疑自己的取数方式，再怀疑被测对象。

规则双向观察覆盖「规则对不对」，不覆盖「我喂给规则的东西对不对」。后者要靠对解析函数
本身做单元测试，而不是靠多测几个样本。
