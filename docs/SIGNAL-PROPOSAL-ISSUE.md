## 你遇到的问题 / The problem

市场「下载」列的周数字有一个高发误读：**发版日的固定开销会被读成采用**。实测展品：`dsh-review-outbox` 周下载 1,997、排名前 6.2%，但前两天占 82%（发版日 11-09 单日 1,131 = 安静日的 8–31 倍），安静日 36–81 落在底噪带（≤40/天，占全目录 58.6%）。裸数字让读者得出「前 6% 的插件」的结论，而它的安静日形状与没人用无法区分。

这不是孤例：全目录抽样三个测量点里 **19.7%–28.3%** 的条目呈单日 ≥5× 中位数的爆发形（结构稳定，占比随目录新增缓升）；同行作者 zuwenyin 在 awesome-dsh-plugin #11870 独立量化其包发版日开销为安静日的 **8.3 倍**。

## 提案（一句话）

列表/市场页的「下载」列：当某包**单日下载 ≥ 周总量 50%**（判定窗口排除最近两天——npm 上报滞后）时，显示「发布日」徽标而非裸数字。**不改排序**，只改展示。

## 依据

**1. 底噪带是结构性的，跨三个测量点稳定**（窗口滑动、结构不动）：

| 测量日（窗口止） | 样本 | 底噪带 | 真实日用 | 爆发形 |
|---|---|---|---|---|
| 2026-11-10（11-08） | 198 | 58.6% | 6.1% | 19.7% |
| 2026-11-15（11-13） | 198 | 60.1% | 8.1% | 28.3% |
| 2026-12-01（11-29） | 200 | *提交日刷新* | *…* | *…* |

约六成条目停在底噪带（每天几十次下载、与是否有人用无关），发版爆发形常驻两成上下（三点区间 19.7%–28.3%，随目录新增缓升）。

**2. 独立同行背书**：zuwenyin 在 #11870 独立确认同一底噪，量化其包发版日开销为安静日的 **8.3 倍**，并以 react（四千万日下载量级）证明上报滞后（最近两天报 0）。不同量级、同一种形状——展品数据见上文问题段。

## 与相邻 roadmap 的关系

#934（最后更新时间显示）与 #1008（体积/兼容矩阵/权限）都是 listing 展示增强，但都不覆盖**下载列的语义**——本提案是第三件独立的展示改进；若维护者更愿意合并处理，本提案的数据与 mockup 可直接并入任一条。

仓库里的 IMPROVEMENT-PLAN.md（v1.0）审计的是安装/更新/错误链路（P0-P2 全在安装侧）；下载列的展示语义在其范围之外——本提案是展示侧的补充，不与该方案的优先级竞争。

## 实现（两个可选接入点，都不需要新数据源）

- **索引携带**：format 1 索引 version 条目含 `publishTimestamp`；UI 判「最新版发布 < 7 天」且「单日 ≥50%」两个条件同时满足时打标。
- **UI 自查**：直拉 npm downloads API 日值序列（`/downloads/range/`），同样两个条件。

## 不做什么

换排序口径 / 换信号源——#13819 已有维护者结论，本提案不动排序。
