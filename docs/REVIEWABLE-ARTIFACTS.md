# 可审阅产物的约定（供插件作者参考）

这份约定回答一个问题：**一个插件把成果交给用户之后，另一个第三方插件（比如审阅队列）怎样才能可靠地把它接过去，而不依赖对方内部实现？**

我们的插件是这条约定的第一个消费者，所以把它写下来，而不是埋在代码里。任何一条都可以被推翻，但推翻需要理由。

## 1. 把「交付」当作事件，而不是函数调用

跨插件协作应该经过会话事件，而不是直接 import 对方的模块。原因是：

- 加载顺序不确定，插件之间可以互不加载；
- 事件有 seq 与时间戳，天然可回溯；
- 消费者可以迟到（历史回填），函数调用不行。

官方 `present` 的 `deliverables/presented` 与 `research_report` 的 `tool/result` 都属于这一类。

## 2. 用「稳定的绝对路径」指认产物

事件里带路径时，请给**解析后的绝对路径**，不要给相对于会话 cwd 的片段。消费者无法可靠地重现你的 cwd 解析规则，而猜错的代价是读不到文件而不是报错。

## 3. 让同一产物的多个版本共享身份

同一份成果第二次交付，不应让消费者以为是两个不同东西。可行的做法：

- 事件里带 `callId`（我们的实现里叫这个），同一 callId 的多次出现视为同一产物的 revision；
- 或者带稳定的 `artifactId`。

只靠文件路径不行——用户在编辑过程中另存为新文件名是常态。

## 4. 区分「产物本身」与「描述产物的元数据」

如果一次交付同时产出正文与清单/签名（例如 `reportFile` + `manifestFile`），请在事件里**分别标明**，不要只给一个目录让消费者自己扫。扫目录会随实现变化而失效，而明确字段是契约。

## 5. 声明哪些字段是契约

一个字段只要被跨插件读取，它就已经是契约了——哪怕文档里写着"内部使用"。建议在 README 或类型定义里显式写一行：

```
下游可依赖：reportFile, manifestFile（tool/result.data.meta）
不保证：目录结构、内部文件名、reportDir 的具体内容
```

## 6. 不要把「审阅状态」写进你的产物

产物的 SHA-256 属于产物；「谁在什么时候通过了它」属于审阅方。混在一起会让同一份字节在不同审阅者之间互相污染。我们的验收单做法是：记下被审阅时的摘要与审阅动作，导出时重算并明确提示"文件已改动，需要重新审阅"。

## 7. 消费者侧的最低要求

如果你是审阅方：

- 只读、不修改原产物；
- 不把正文内容上传或写进日志；
- 记录的是摘要与决策，不是内容副本；
- 文件变了要能说出来，而不是假装通过仍然有效。
