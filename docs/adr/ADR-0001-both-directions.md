# ADR-0001 每条检查规则必须在测试里被观察到两个方向

状态：已接受
日期：2026-11-19

## 背景

2026-11-19，把 vertical-kit 的二十个检查逐个指向本项目自己真的在发的文件。四个包报错了，而且都是同一个形状：规则对**一切合法文档**报错。

- `dsh-commit-msg-check` 的 `type-missing` 对 102 条真实提交中的 85 条（83%）报错。其中 61 条只是没写 Conventional Commits 前缀，那是团队约定，不是缺陷。
- `dsh-onboarding-check` 的 `success-missing` 对 23 个真实 README 中的 20 个报错。它们都写了逐字真实输出，只是标题叫「真实输入输出」而不是检查要求的「你应该看到」。
- `dsh-release-notes-check` 的 `version-missing` 对 3 个真实 CHANGELOG 全部报错。它们用的是 `## [1.2.0] - 2026-11-17`，也就是 Keep a Changelog 规定的写法；检查只认 `## 1.2.0`。
- `dsh-pr-description-check` 的 `what`/`why`/`test` 对 19 个真实已合并 PR 全部报错。三个问题都用英文正文答了，只是没按小标题写。

这四个包的单元测试**全绿**。原因是同一个：每条规则只在「坏文档让它报」这个方向被断言过，从来没有一条测试说「这是一份好文档，它必须什么都不报」。

## 决定

每条规则必须有两条测试：一条让坏文档触发它，一条让好文档不触发它。这条要求由 `dsh-vertical-kit/scripts/audit-rules.mjs` 自动执行，接在 `npm run check` 里，覆盖失败即阻断。

「不触发」的判定接受两种证据：一是针对该规则的否定断言（`!findings.some(f => f.rule === 'x')`），二是包级别的干净用例（`deepEqual(findings, [])`、`errors, 0`、`ok, true`），后者一次性覆盖全部规则。

## 后果

好处：

- 落地当天跑出 148 条规则里 148 条双向覆盖，并找出两条**永不触发**的死规则：`subject-empty`（`HEADER` 要求冒号后 `.+`，`feat:` 根本解析不成类型）和 `sku-empty`（`pick()` 有意跳过空值，"有列但单元格为空"被当成"没有列"）。两条都改成可达。
- 顺带发现 13 条规则只有静默方向，从没在测试里触发过——一个从没报过的规则没人知道它能不能用。
- 这条约束是可以被机器人检查的，所以它不会随着会话结束而失效。

代价：

- 每条规则多写一条测试，二十一个包、148 条规则，写的时候确实慢。这部分成本一次性付出，之后每个新规则都要付。
- 「干净用例」这个证据是包级的，不是规则级的：一个包有干净用例，就默认它所有规则在好文档上都不报。这是为了不强迫每包写 148 条断言做的妥协，它比没有强，但比逐条断言弱。
- 审计靠正则读测试源码，不是真的执行；写法奇特的断言可能被漏判。今天 148/148 是通过的，但这个数字的含金量受限于审计脚本本身。

## 备选方案

- **只靠 dogfood**：把每个检查指向真实文件并要求零报错。更强，但只覆盖有真实语料的四种文档（README、CHANGELOG、LICENSE、提交信息）；invoice、resume、meeting-notes 这些没有第三方真实语料，覆盖不到。
- **只靠人工评审规则**：这次就是这样做的，四个包都过了评审。人工看不出"这条规则从没在好文档上跑过"。
- **要求每条规则两条测试，但靠 grep 规则名字符串判断**：最便宜，也最容易被"名字出现在注释里"骗过，等于没有。

## 备注

两条一起用：审计保证"每条规则双向有测试"，dogfood 保证"真实文档上零报错"。前者管形状，后者管事实。
