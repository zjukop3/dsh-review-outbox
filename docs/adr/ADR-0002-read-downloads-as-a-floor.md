# ADR-0002 下载量只读成底噪带，不读成用户数

状态：已接受
日期：2026-11-18

## 背景

本项目发布 26 个包之后，周下载数落在 1,755–1,997 之间。这个数字看起来像"有一千多人在用"，值得先确认它是不是真的。

做法是把目录里所有条目的日下载序列拉下来，按形状分类。结果分三类：

- 一类是**单日爆量**：一周的量有一半以上集中在一天，其余六天接近零。人不会这样用东西。
- 一类是**停在底噪带**：每天 20–40 次，几乎不动。三个时间点采样结果是 58.6%、60.1%、63.8% 的条目落在这条带里。
- 一类是**头部**：尾巴（每周后三天的均值）在 117–180 之间，持续。

关键的一步是**离散度检查**：如果多个包的日序列两两之间高度相关，它们就不是多群独立用户，而是一个客户端在按固定节奏请求。本项目的九个包尾巴是 117/119/121/122/164/171/178/180，变异系数 0.186；作为对照，目录头部十二个条目两两相关的中位数是 0.299，变异系数 1.617，只有 12.1% 的配对相关系数 ≥0.5。

## 决定

周下载数不解释为用户数。本项目自报的口径是：

1. 停在底噪带的条目**不算有人装**，无论周数字是三位还是四位。
2. 一个包的下载曲线如果和同作者其他包的高度同步（变异系数 < 0.25），按单一自动化客户端计算一次，不按包数累加。
3. 真正的采纳指标不取下载量，取**被人审阅并处置过的成果数**（pending 队列里人类决策的条数）。这个数现在是 0。

## 后果

好处：

- 站点上所有下载相关的表述都改成"底噪"和"形状"，不再暗示用户量。`docs/READING-DOWNLOADS.md` 把三类形状、离散度规则和反向自检写成可复现的脚本，任何人都能对我的包跑一遍，验证我的结论。
- 这条规则当场纠了一个自己的错误：最初的组合结论把五个包判成"持续高于底噪，可能是真实使用"，离散度一算，是一个客户端的一个频率。

代价：

- 对外沟通变难。别人问"多少人在用"，答案是"不知道，而且这个数字回答不了这个问题"——这比给一个漂亮数字难说得不到即时反馈：没有正面数字，就没有可以贴到社交平台的进展。
- 采纳指标取人类决策数，意味着这个数会长期是 0，而 0 看起来像"什么都没发生"。要让项目看起来在动，只能靠产出可复现的资产（形状分类、离散度脚本、底噪基线），而不是靠一个上涨的曲线。
- 变异系数阈值 0.25 是我在一个目录上标定的，没有第二份独立数据验证。它可能是这个目录的特性，不是普遍规律。

## 备选方案

- **直接报周下载数**：最省事，也最容易误导。1,997 次/周听起来像产品有起色，实际上和 20 次/天没有区别。
- **只看包数增长**：更像在做事（目录条目数、发布包数），但这两个数都可以通过堆量刷高，和"有没有人用"无关。
- **用 npm 的 unique downloader 数据**：npm 官方不提供免费接口，第三方估算服务的口径不透明，不值得为一句话引入一个不可复现的数据源。

## 备注

这条决策的检验方式是反向的：任何人可以对目录头部跑同一个脚本，如果头部也呈现出同样的高同步性，说明 0.25 这个阈值把真实用户也判成了机器人，结论要推翻。
