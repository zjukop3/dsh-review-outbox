# 假设与证伪条件（2026-11）

这份文件存在的目的：把「要不要继续做这个产品」变成一个**有定义、可判定的问题**，而不是靠情绪或沉没成本决定。

## 当前假设

> DSH 用户会因为「Agent 交付的成果需要人工验收」而安装 Review Outbox，并且装上之后**真的会去做验收动作**。

拆成两个可独立证伪的部分：

- **H1 需求成立**：有人愿意为「证据门 + 版本绑定的验收单」安装插件。
- **H2 行为成立**：装上之后，人会在队列里做处置（通过/退回/归档），而不是让它继续堆。

## 证伪条件（写到可以按日期判定）

| 编号 | 条件 | 判定时点 |
| --- | --- | --- |
| F1 | 日常 Profile 升到 0.1.4 之后的一周内，人工动作仍为 0 | 2026-11-17 |

## 已经拿到的证据

支持需求存在：

- 目录 4,985 条目、321 个 workflow 插件、其中 68 个与审阅/验收沾边；邻接插件月下载 700–3000。
- 「带版本绑定的交付回执」已有人做（`@oxmumu3/dsh-delivery-receipts`），说明这一层有真实需求，不是幻想。
- 我们自己 47 天里产生 75 条交付物 —— 交付密度确实高。

反对「我们能拿到它」：

- 真实人工动作 **0**，最久待审项已放 47 天。
- npm 下载 497 全部集中在发布当天，其余为 0，无法归因给人。
- 自身定位曾被证伪一次（回执不独特），已改为「证据门」。
- 「诊断/更新排障」方向查证后放弃：目录里已有 88 个同类。

## 候选替代假设（按证据强度排序）

### T2：成为「交付物生成类插件」的默认验收层

**问题**：`dsh-research-report`、`dsh-media-desk` 这类插件的用户已经拿到成果，他们缺的是"决定它算不算完成"，而不是又一个生成器。
**为什么不是拥挤区**：验收层目前只有回执类工具，没有人做"生成方 → 验收方"的默认衔接。
**第一个实验**：把集成做成零配置（新密封报告自动进队列，已实现），然后向上游文档提"下游验收"一节的小 PR；被拒就停。
**杀死条件**：两次上游 PR 均被拒，且无用户主动询问集成。

### T3：把方法论本身做成资产，而不是插件

**问题**：我们真正稀缺的产出是"实测出来的插件运维与验收方法论"，不是又一个 UI。
**为什么可能有效**：手册页、清单页、`checklist.txt` 都能被搜索引擎与 LLM 直接引用，不依赖安装。
**第一个实验**：把手册扩成可被引用的规范（含可复现命令与失败案例），并保证每一条都能被独立验证。
**杀死条件**：四周内页面没有外部引用、没有自然搜索流量（用 IndexNow 之外的证据判断）。

### T4：接受「小众但留存」的定位

**问题**：也许这个产品只需要服务几十个重度用户。
**含义**：不再追求目录排名，把力气放在"用的人离不开"——例如验收单成为对外交付的标准附件。
**杀死条件**：连这个作者本人（唯一确认的候选用户）都不用它。
